## 背景（测试会话的生产构建实测）

生产构建下，**详情页首屏加载完成后的一小段时间窗内**点击话列表条目或主按钮，`<Link>` 的处理函数跑了（事件被 preventDefault）、导航用的 RSC 请求也 200 返回了，但**路由没有提交**：地址栏与页面都不变，没有任何报错，用户必须再点一次。

- 触发条件：与首屏 5 条 `<Link>` 的 `Next-Router-Prefetch` 请求是否在途强相关；把预取请求全部 abort 后，20×3 复跑 **0 失败**（基线 1/20 失败）。
- 影响面：F4-4 / F4-6 / F4-7 / F5-7 / D-016-② / D-016-③（这些用例的第一步都是「从详情页点某话」），每轮全量有 3～5 条踩中。
- 归属判断：这是 Next.js App Router（`next@15.5.26`）在并发预取下的客户端路由行为，我们的代码无法直接修框架，只能调整使用方式。

## 要做的事（架构师裁决：D-020）

1. **详情页的话列表链接关闭预取**：给 `ChapterList` 里每个话条目 `<Link>` 加 `prefetch={false}`，让点击永远走一次真实导航，消除「并发预取在途」这个窗口
2. 主 CTA（`ProgressCTA` 的「继续阅读 / 开始阅读」）**保留默认预取**（只有 1 条，且是最高频动作）
3. 在代码注释里写清「为什么关预取」——把 F-06 的现象、触发条件与取舍写明白，避免后人"优化"回去
4. 补单测：断言话列表链接带 `prefetch={false}`（可用 `data-prefetch` 或组件 props 断言；若 `next/link` 的 prefetch 不落到 DOM，就改成对链接渲染的等价断言 + 注释说明）
