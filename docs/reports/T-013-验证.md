
## 5. 红灯项（保留，未改断言）

### 5.1 F-06（缺陷 · **高** · 归属：需架构师裁决 → 大概率是 Next.js App Router 客户端路由行为）

**现象**：生产构建下，在**详情页刚加载完**的时间窗内点击话列表条目 / 主按钮，
`<Link>` 的处理函数确实运行了（事件被 preventDefault），但**路由没有提交**：
地址栏不变、页面不变、无任何报错、无任何用户反馈。用户必须再点一次。

**触发条件（A/B 实测）**：与首屏 `<Link>` 预取请求（`Next-Router-Prefetch`）是否在途强相关。

**最小复现（本机稳定复现，约 1/20）**：

```powershell
# 1) 生产构建 + 起服务
pnpm build && pnpm exec next start -p 3100
# 2) 把「详情页点第 3 话」这一步复制成 20 次 × 3 worker 复跑
pnpm exec playwright test e2e/tmp-debug.spec.ts --project=chromium --workers=3 --repeat-each=20
```

**实测数据**：

| 变体 | 结果 |
| --- | --- |
| 基线（照抄 D-016-② 第一步） | **1/20 失败**（另一次同样 1/20） |
| 变体 B：把 `next-router-prefetch` 请求全部 abort（只放行导航 RSC） | **0/20 失败** |
| 真实全量里的表现 | 每轮 3～5 条用例踩中（F4-4/F4-6/F4-7/F5-7/D-016-②/③） |

**失败现场的探针证据**（`addInitScript` 注入的点击/导航日志）：

```
COPY-FAIL {"path":"/comics/xinghai",
  "navLog":["replace:/comics/xinghai"],          # ← 只有水合时那次 replace，没有任何 push
  "clickLog":[
    "capture:/comics/xinghai/3:reactProps=true:defaultPrevented=false",   # 命中的就是正确链接，且已水合
    "bubble:/comics/xinghai/3:defaultPrevented=true:path=/comics/xinghai" # 处理器跑了，阻止了默认跳转
  ]}
  events=[]                                       # 没有 pageerror、没有 console.error
```

另一次失败保留了 Playwright trace，可见**导航用的 RSC 已经成功返回**、目标路由的客户端 chunk 也 200 加载，
但 URL 始终没有变：

```
200 GET fetch /comics/xinghai/3?_rsc=sH353DWge62C0v-6      ← 导航 RSC，200，6.8ms
200 GET script /_next/static/chunks/app/comics/%5Bslug%5D/%5Bchapter%5D/page-c91d28981494aa6c.js
```

**为什么 dev 没发现**：dev 下构件按需编译、预取与水流时序完全不同（T-009/T-011 两轮 102 次执行都没出现），
prod 下首屏 5 条预取在极短时间内并发，窗口更集中 —— 这正是 D-019 要求验生产产物的价值。
注意：窗口长度随网络 RTT 放大（本机同机 RTT≈0 都有 5% 命中），真机慢网下用户「页面已可见就点一下」更容易踩。

**建议的方向（交实现者/架构师判断，不在我的可改目录内）**：

1. 给章节列表的 `<Link>` 加 `prefetch={false}`（或 `prefetch={null}`），让点击总是走一次真实导航；
   代价是点击后多一次 RSC 往返（可接受：详情页只有一个入口动作）。
2. 或让详情页首屏不要同时发起 5 条预取（例如只预取「继续阅读」目标）。
3. 或先验证是否 Next 版本问题（当前 `next@15.5.26`）：升/降一个小版本后重跑本用例对照。
4. 无论怎么修，**请保留这条复现路径**：它是本轮唯一能稳定抓住该竞态的用例。

### 5.2 F-07（测试自身的中间断言过时 · 归属：测试工程师，需架构师点头才改）

`F5-4b【缺陷 F-01】…` 这条用例是 T-009 为留痕缺陷 F-01 写的：先断言「话末出现『下一话 · 第 4 话』区块」，
再断言「第 4 话内容已接续」。T-011 把接续改成 effect 补判定后，接续发生得非常快（T-011 实测 25–37ms），
于是第一句断言变成竞态：快的时候区块一闪就被第 4 话内容顶掉（§3.2 的 DOM 快照就是现场）。

**我的处理**：按「不许改断言」的硬约束，**本轮保持红灯不动**，只报告。请架构师裁决其一：

1. 授权把它改写成「修复后回归用例」：删掉那句中间断言，只保留实质断言（一步到底 + 停住后
   `[data-section="4"]` 出现、顶栏/地址同步为第 4 话）；
2. 或者删掉这条留痕用例（F-01 已有 `F5-4` 主路径 + T-011 新增的 3 条单测覆盖）；
3. 或者保留现状（接受它是随机红灯）——不推荐，随机红灯会掩盖真问题。
