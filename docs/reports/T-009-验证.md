## 5. 缺陷与观察

### F-01（缺陷 · 中 · 归属：全栈工程师 / `src/components/ReaderStrip.tsx`）

**现象**：阅读页停在文档底部后，下一话不会自动接续；必须再产生一次滚动位移（或点
「继续阅读」区块）才接上。直接违反 PRD F5-4「继续向下即呈现第 4 话内容」，并连带
使 F5-11 的「进入第 4 话时该图无需重新加载」在该路径下无从验证。

**最小复现步骤**（Chromium 与 WebKit 均复现）：

1. `pnpm dev`，打开 `http://localhost:3000/comics/xinghai/3`，等首屏出现第 1 页图（等水合）；
2. 执行 `window.scrollTo(0, document.documentElement.scrollHeight)`（等价于：拖滚动条到底 / 按 End / 快速甩到底后停住）；
3. 等 2.5 秒：Network 里 `/api/comics/xinghai/chapters/4` 已 **200**，页面上「下一话 · 第 4 话 / 日志第七页 / 继续阅读」区块可见，但 `document.querySelector('[data-section="4"]')` 仍为 **null**；
4. 继续向下滑（已在底部、位置不变）仍无变化；向上滚 120px 后 `[data-section="4"]` 才出现。

**根因分析（读码 + 实测）**：「预取完成 → 追加下一话」的判定只写在 `scroll` 事件回调里
（`ReaderStrip` 的滚动 effect：`if (block && nextChapter && nextStatus === "ready")`）。
数据是在滚动停止之后才回来的，此时不会再产生新的 `scroll` 事件，于是追加逻辑没有机会执行。
连续慢速滚动（每 0.5 屏 / 120ms）时数据在滚动过程中回来，因此主路径正常 —— 这也解释了
为什么 F5-4 主路径用例通过、而本条用例失败。

**建议修法（交实现者判断）**：把「话末区块是否已进入视口」的判定从纯 `scroll` 事件里挪出来，
例如在 `nextChapter/nextStatus` 变为 ready 时用 effect 补一次判定，或给话末区块挂
`IntersectionObserver`（与懒加载同一套机制），不要只依赖滚动事件。

**留痕用例**：`e2e/reader.spec.ts` → `F5-4b【缺陷 F-01】直接跳到底部并停住时，第 4 话应当自动接续`
（当前预期红灯，修好后应当转绿，不需要改测试）。

### F-02（观察 · 低 · 同一代码路径）

进度写入（500ms 防抖）同样只由 `scroll` 事件驱动。实测：如果第一次滚动发生在客户端水合
完成**之前**，且之后不再产生滚动事件，那一次停顿不会写入 localStorage（E2E 里表现为
WebKit 上的时序假失败，加「等水合」后消失）。真实用户几乎不会命中（水合约 0.3～1.5s，
而写入需要「滚动停止」这一前置动作），但和 F-01 属同一类脆弱点，建议一并用 effect 兜底。

### F-03（待裁决 · PRD 与 ui.md 口径冲突）

PRD **G7** 第一句要求「站点名『漫画站』在页头可见」，但 `docs/specs/ui.md` §5.4 把阅读页
顶栏定为「‹ 返回详情 + 漫画名 + 详情」——没有站点名，也没有直达首页的入口（阅读页回首页
需要「返回详情 → 返回首页」两跳）。E2E 按 ui.md 的实况断言（用例名已注明「回首页需经详情页两跳」），
没有把这写成红灯，因为两份冻结文档互相矛盾，需要架构师裁决：

* 若以 ui.md 为准 → 请修订 PRD G7 的措辞（阅读页只承诺「可回到详情」）；
* 若以 PRD 为准 → 补一条任务给阅读页顶栏加站点名/首页入口。

### F-04（工程环境 · 已验证并规避）

Playwright 默认把 trace / 截图写进 `testDir` 附近的 `test-results/`。在 `next dev` 同时运行
时，这些写入会触发 dev server 反复重编译（日志里成片的 `✓ Compiled in …`），重编译会中断
客户端软导航（RSC 请求 `net::ERR_ABORTED`），表现为**点链接地址栏不动** —— 第一次全量跑时
28 条用例因此集体假失败，单条调试用例也稳定复现；把产物目录移到仓库外后同一用例立刻恢复正常
（A/B 对照见 §2.5 与 `playwright.config.ts` 顶部注释）。

因此 `playwright.config.ts` 把 `outputDir` 与 html/json 报告默认写到系统临时目录
（`%TEMP%\comic-site-e2e\`，可用 `E2E_ARTIFACT_DIR` 覆盖）。**若将来要把产物放回仓库，
必须先解决这个交互**（加 watcher 忽略或换端口跑 E2E）。CI 的 `e2e` job 目前是 `if: ${{ false }}`，
启用时其 `path: playwright-report/` 也要一并改（该文件不在本任务可改范围）。

### F-05（测试口径说明 · 非缺陷）

`F5-10` 的懒加载在 1280×720 下只有第 1 页在首屏挂载（第 2 页需要滚动才挂载），这与实现里
「视口下方 200px 才挂载」的设计一致，不是缺陷；用例据此断言「未滚动时远端页（第 10 页）不
发请求、滚近后才发」。同理，`F5-12` 的用例会先等水合、再按阅读节奏逐页滚动，避免「滚太快
导致观察器错过页面」造成的假阳性。

## 6. 未自动化条目（原因 + 手工步骤）

### 6.1 G4「整话/整页加载失败 → 错误态 + 重试」中的**路由级**部分

**原因**：数据来自仓库内的 `data/comics.ts`，没有可断网的外部依赖；在浏览器层拦截客户端软
导航的 RSC 响应后，Next.js 会退回整页导航（MPA fallback），用户仍能到达目标页 —— 错误边界
`src/app/error.tsx` 反而不会被触发（实测：URL 抵达 `/comics/slow-cooking`、标题正常渲染）。
因此错误边界的**渲染与重试**由单测 `tests/components/error-and-not-found.test.tsx` 覆盖，
E2E 改断言「回退后用户仍可达目标页，且无错误堆栈」。

**手工步骤（需要在真实故障下确认一次）**：

1. `pnpm dev`，临时在 `src/app/comics/[slug]/page.tsx` 顶部插入 `throw new Error("boom")`；
2. 打开 `/comics/xinghai` → 应出现「内容加载失败」+「网络或数据服务暂时不可用，请稍后重试。」
   +「重试」「返回首页」，无堆栈、无白屏；
3. 删除该行（恢复原实现）后再点「重试」→ 内容正常渲染；
4. 图片级失败已自动化（`global` G4 用例用请求拦截制造），无需手工。

### 6.2 G5 浏览器矩阵的未覆盖部分

**原因**：本机只有 Chromium 与 WebKit 两个引擎可用；Edge、Safari 的两个具体大版本、
iOS Safari、200% 缩放、真实 `env(safe-area-inset-*)` 无法在 CI/本机自动覆盖。

**手工步骤**：

1. Chrome / Edge（最近两个大版本）各在 360×640 与 1440×900 走一遍首页 → 标签筛选 → 详情 → 阅读页接下一话；
2. Safari 桌面：同上，并确认阅读页底栏不被手势条遮挡（safe-area）；
3. iPhone Safari：横竖屏切换各看一次，确认「无横向滚动、输入框不触发页面放大、吸底主按钮不压手势条」；
4. 任意浏览器把缩放调到 200%，确认标签 chip、卡片、话列表条目仍不重叠、可点击。

### 6.3 G6 Safari 默认键盘设置下的 Tab 顺序

**原因**：Safari/WebKit 默认关闭「按下 Tab 键高亮网页上的每个项目」，Tab 会跳过链接，
因此「站点名 → 搜索框 → … → 标签 → 卡片」的 Tab 序列在 WebKit 上按浏览器默认行为不成立
（这是浏览器偏好，不是站点缺陷；站点用的是原生 `<a href>`）。该条用例只在 Chromium 跑，
WebKit 侧另有一条通用用例验证「可点元素都是原生 `<a>/<button>`、可聚焦、Enter 可激活」。

**手工步骤**：Safari → 设置 → 高级 → 打开「按下 Tab 键高亮网页上的每个项目」，重跑
`pnpm exec playwright test --project=webkit -g "Tab 顺序"`（把该用例的 `@webkit` 标签加回即可）。

### 6.4 F6-4「换另一台设备」的字面验证

**原因**：E2E 用独立 browser context（等价于另一浏览器配置目录）近似；真正的另一台设备
无法自动化。已由 `progress` F6-4 覆盖「新 context 里没有进度、从第 1 页开始」，
设备间不共享这一点由架构（localStorage）保证。

### 6.5 视觉回归（可选的后续增强）

本轮 F5-12 用「页块文档坐标前后完全一致」做精确断言（比截图 diff 更硬），未做像素级
截图基线；若后续要防「颜色/间距被误改」，建议另开任务引入 `toHaveScreenshot` 基线，
并把基线图放在仓库外的产物目录（原因见 F-04）。
